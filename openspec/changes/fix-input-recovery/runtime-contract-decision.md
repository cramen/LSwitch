# Решение о контракте обычной конвертации

Статус: выбран вариант B 16.10.2026. Пользователь явно поручил принять решение
самостоятельно для качества приложения. Specs/design обновлены; production-допуск
ещё не выдан, реализация и приёмка нового профиля остаются работой этого change.

## Что блокирует подключение

Исходный контракт требовал доказанного завершения каждой собственной команды до
обычной доставки удержанного ввода. AX/clipboard/Unicode production factories
такого подтверждения пока не предоставляют. Включение ledger без нового provider
превратит обычные конвертации в отказ до изменения текста; возврат к старому
безусловному release сохранит исходный P1.

Проверенный per-PID tap подтверждает допуск/отклонение события, но не выполнение
редактором. Уже admitted native-пакет в наших опытах исполнялся после закрытия
поколения. AX RPC через этот tap вообще не проходит. Это установленное ограничение
текущего решения, а не доказательство невозможности любого будущего адаптера.

Apple описывает [AX setter](https://developer.apple.com/documentation/applicationservices/1460434-axuielementsetattributevalue)
и [успешный AXError](https://developer.apple.com/documentation/applicationservices/axuielement_h),
но найденная документация не устанавливает отдельный token-bound commit/cancel fence
редактора. [CGEventTapPostEvent](https://developer.apple.com/documentation/coregraphics/cgevent/tappostevent(_:))
задаёт порядок внедрения событий в поток, не подтверждение применения текстовой модели.
Отсутствие найденного контракта не подменяется утверждением об отсутствии всех возможностей macOS.

## Вариант A: сохранить текущий строгий критерий

- Искать и принимать отдельный достоверный completion/ordinary-delivery contract
  хотя бы для одного конкретного редактора.
- Пока такого контракта нет, новый путь отказывает до мутации; его включение
  без доступного provider нельзя объявить функционально готовым исправлением.
- Новые компоненты и UI могут быть завершены независимо, но общий change остаётся
  открытым. Срок разблокировки по имеющимся доказательствам не установлен.

## Вариант B: принять проверяемый практический контракт

Принятое изменение требований:

- Обычный успех допускается по контракту конкретного проверенного профиля:
  результат системного вызова, порядок собственных отправок и полная проверка
  ожидаемых текста/каретки/контекста. Первым кандидатом служит прямой AX в TextEdit;
  native/clipboard и другие приложения проходят собственную приёмку отдельно.
- Такое основание хранится как наблюдаемый подтверждённый результат профиля,
  а не вымышленный renderer ACK или доказанная отмена команды.
- Error, timeout, смена контекста, потеря прав, неоднозначное чтение и неизвестная
  отправка остаются unknown: без повторной записи, success receipt и автоматического
  replay. Уже принятый ввод передаётся в RAM recovery.
- Неизвестные профили отказывают до мутации. Потеря управления дальнейшим физическим
  вводом честно отображается; OFF и явный выход не объявляют поле исправленным.
- Полная событийная матрица, сохранение clipboard, точный undo, лимиты и проверки
  гонок сохраняются. Защита от произвольного будущего изменения текста самим
  сторонним приложением после проверки результата не обещается.

Вариант B позволяет работать над пригодным обычным режимом, но меняет требование
о доказанном завершении каждой команды. Решение отражено в specs и D1.1;
ledger/provider и production factory включаются только после реализации и проверок.
